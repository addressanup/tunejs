# Backend feasibility decision — 2026-09-06

**Provisional choice: reuse Web Audio for the browser first-sound foundation; evaluate React Native Audio API 0.13.3 behind the same narrow adapter. Do not freeze the full v0.1 backend yet.** Keep the C++/WASM experiment as a comparison, not a production dependency. There is executable code now, but this is a development snapshot, not the v0.1 preview.

The first-release specification remains authoritative. Neither native spatial support nor physical-device reliability has been demonstrated. Native HRTF and capture timestamp semantics are decision gates before building the three full creative workflows on this foundation.

## Candidates and contract gaps

**Web Audio built-ins.** Reuse provides scheduled sources, gain/filter automation, stereo panning, offline output and HRTF without shipping a custom renderer. The fixtures establish a useful starting point. Browser-provided HRTF data lacks an application-controlled versioned asset identity, so simply wrapping PannerNode would not yet meet the project's reproducible asset contract. A first-party integration with documented assets and reference data is still needed. Capture needs AudioWorklet delivery and bounded queues, with clock discontinuity handling.

**React Native Audio API 0.13.3.** Inspected the exact npm tarball: 1,796,509 bytes compressed, 9,398,233 unpacked, SHA1 `87b17cc1e76d3a07a189a3dda767b1584d484ad8`, MIT package metadata. The installed stable API supplies oscillator/gain/filter/stereo panner/offline contexts. It uses `onEnded`, unlike browser `onended`; the adapter normalizes this. AudioRecorder's callback contains `{buffer, numFrames, when}`, where `when` is relative to recording start, not the engine clock. A verified clock mapping plus overflow detection is necessary for TuneJS taps. The published [coverage table](https://docs.swmansion.com/react-native-audio-api/docs/other/web-audio-api-coverage/) and installed source both lack PannerNode/AudioListener in stable 0.13.3. “Next” documentation is not evidence of a released, validated implementation.

Android arm64 `assembleRelease` succeeded in 1m 53s after dependency repair and cleanup. A final 10-second incremental build explicitly rebundled the current package (1,108 JS modules); the APK and its SHA256 are retained. No Android runtime or physical-device run occurred.

The iOS Release arm64 simulator build also succeeded, and the app launched on the iPhone 17 Pro simulator running iOS 26.5. The same native OfflineAudioContext fixtures produced five passes, one strict timing failure and two explicit HRTF-unavailable results. Stereo-pan/mirror error was 1.49e-8 at both rates; filter output was finite and repeatable. Timing error was zero at 48 kHz. At 44.1 kHz, requested frame 1023 rendered at frame 1022, producing 0.499755859375 full-buffer difference. A diagnostic repeat retained the original failure and measured onset error of one frame, with gain error zero at actual onset. Upstream `AudioUtils.h` truncates `time * sampleRate`; `(1023 / 44100) * 44100` evaluates to `1022.9999999999999`. This explains the observed shift. It meets the specification's proposed <=1-sample onset target, but does not pass this stricter exact-buffer fixture or establish the full timing contract. Do not loosen the raw fixture tolerance. This needs explicit frame conversion semantics before transport/offline projects grow.

Earlier iOS attempts failed first on a missing EXConstants modulemap while pod regeneration overlapped compilation, then on disk exhaustion while compiling RNGestureHandler. The first was a procedural failure, not an audio-backend finding. Removing only task-generated build intermediates allowed sequential rebuilding to succeed. The successful native runtime evidence is **simulator offline PCM**, not microphone, device-output, physical interruption, latency or listening validation. Source, lockfiles, app/APK and logs are preserved; large compiler intermediates were cleaned up.

A clean native application type-checks the real AudioContext against TuneJS's host interface without a cast or application audio callback. React Native 0.86.3, Expo 57.0.20, React 19.2.3 and Hermes are pinned by the app lockfile. The public audio package entry imports AudioControls, which required react-native-gesture-handler 2.32.0, react-native-reanimated 4.5.1 and react-native-worklets 0.10.1 to bundle. The first Android release attempt failed on this missing dependency. This is a concrete packaging cost; no UI dependency was added to TuneJS core. Native external codecs/libraries are downloaded by upstream build scripts; the native audio external directory measured 53 MB after Android download. This is not the final APK overhead. The example's npm audit reports 10 moderate transitive issues; no blind breaking upgrade was applied.

**Custom C++/WASM + native I/O.** The tiny comparison kernel proves shared arithmetic is achievable, but does not establish timing under load, graph lifetime safety, capture, mobile sessions, packaging, or binaural quality. Miniaudio offers device callbacks and other reusable infrastructure ([official manual](https://miniaud.io/docs/manual/index.html)); that still leaves TuneJS to own a renderer, command queue, bridge, interruption policy and HRTF integration. There is insufficient evidence to justify that maintenance commitment now.

**Other reuse options.** [Tone.js](https://tonejs.github.io/) supplies browser musical abstractions and is useful as a future workflow comparison, but was not benchmarked and does not itself establish this native contract. [Expo Audio](https://docs.expo.dev/versions/latest/sdk/audio/) supplies player/recorder/session facilities, but is not a substitute for the tested composable DSP/offline node path. Neither is rejected on performance grounds. No speculative shared engine was selected just because the architecture draft proposed one.

## Wave 2 frame-conversion outcome — 2026-09-12

The engine now schedules voice start/stop on whole frames and asks the adapter for the host seconds value that lands on that frame (`Adapter.hostTime`). The browser adapter passes `frame / sampleRate`, matching the exact browser placement recorded above. The native adapter passes `(frame + 0.25) / sampleRate` because the installed React Native Audio API truncates `time * sampleRate`; a quarter-frame bias stays on the target frame under both truncation and nearest rounding. A fixture-version-3 run on the iPhone 17 Pro simulator (iOS 26.5, Release) placed all twelve impulses on their requested frames at 44.1 and 48 kHz with zero strict buffer error when scheduled through that conversion, while the raw-seconds run reproduced the 1023→1022 shift. Snapshots: `docs/evidence/2026-09-12/`. Parameter automation still uses host seconds and may land one frame early on native, inside the specified onset tolerance. Live-context, transport and physical-device timing remain unverified; the raw fixture stays in the suite as the host-limitation reference. The same fixtures on the Android arm64 API 35 emulator matched the iOS simulator sample-for-sample, including the HRTF unavailability, so the frame-conversion finding and the missing native spatial primitives apply to both React Native platforms in 0.13.3.

Sample assets decode PCM WAV in TuneJS and resample to the context rate with a fixed 64-tap Kaiser (β = 12) windowed sinc rather than relying on host resampling, so the decoded material is identical on every host before it reaches the graph; a 1e-5 tone fixture bounds that resampler. Delay effects must avoid host feedback cycles: the React Native Audio API graph documentation states it may silently drop an edge that would form a cycle, so TuneJS effects use finite feedforward structures (multi-tap delay, convolution reverb with a generated impulse response) that render identically on both hosts.

**Fixture-version-4 mixing results (2026-09-12).** The browser passes the delay-chain and convolver-identity fixtures at both rates. The native host fails both, identically on the iOS simulator and the Android emulator: the delay-chain output is a single frame-0 impulse carrying one tap gain (0.125 on iOS; 0.25 or 0.5 on Android with a 0.375 repeat error, i.e. nondeterministic offline rendering), and the convolver deviates from the supplied response by up to 4.7% of full scale while remaining repeatable. Consequently `delay()` and `reverb()` are browser-verified only; native effect parity is a release gate. See `docs/evidence/2026-09-12/mixing-fixtures-analysis.json`.

**Fixture-version-5 topology probes (2026-09-12, three launches per platform, all identical unless noted).** A single DelayNode renders its impulse at frame 0 instead of frame D: the native offline DelayNode applies zero delay. A source fanned out to two gains that both feed the destination yields only the last-connected path (0.5 instead of 1.5), and two sources feeding the destination directly yield 1 instead of 2: the native destination delivers one input rather than a sum, and which input survives varies with graph-event ordering (the delay chain's surviving tap alternated between launches). Twelve sources fanning into a GainNode already summed correctly in the timing fixture, so the defect is specific to the destination. The convolver output has no lag and a 0.2–0.3% scale deficit, but a residual of up to 4.9% of full scale remains after fitting, identically on every launch. Decisions: (1) TuneJS owns a unity master GainNode as `engine.output`'s host with one edge into the destination; (2) the Delay effect and any delay-based binaural cue remain browser-only until the host DelayNode changes; (3) offline rendering must not assume host-convolver equality across platforms. Raw files: `docs/evidence/2026-09-12/topology/`.

**Live-context probes (2026-09-12, version 2, two launches per platform, identical on iOS simulator and Android emulator).** Measured through an AnalyserNode with the audible path muted: two constant sources into one GainNode sum to exactly 0.5 (fan-in works live); a fan-out-free two-source delay probe shows the DelayNode delaying exactly 480 frames (the live DelayNode works; the zero delay is offline-only); but a node connected to two branches that reconverge delivers only the last-connected branch (0.125 instead of 0.375), whether the branching node is a source or a GainNode. Headless Chrome passes all four. **The native host keeps one outgoing connection per node, live and offline.** Consequences: (1) polyphony and buses (fan-in) are sound natively; (2) every parallel wet/dry structure — `delay()`, `reverb()` — and any user-level fan-out is broken natively, so the native adapter now declares `hostLimits.fanOut = false`, a second outgoing connection rejects with `UNSUPPORTED`, and `delay()`/`reverb()` reject with `UNSUPPORTED` on that host rather than silently rendering one path; (3) native offline rendering through the host graph is unusable beyond single chains (no summation, no delay), so deterministic offline rendering (Wave 7) must be TuneJS-owned; (4) the sustainable native path for effects, binaural rendering and offline output is a single-node TuneJS DSP processor (AudioWorklet in browsers, React Native Audio API worklet processing node natively) with shared JS DSP — to be evaluated with a fixture before Wave 5 spatial rendering claims native support. Raw files: `docs/evidence/2026-09-12/live-probes/`.

**First physical device (2026-09-12).** A Nothing A059P (Android 16, arm64) running the same Release APK reproduced every emulator result exactly — offline fixtures, topology probes and live probes — so the findings above are hardware-confirmed host behavior, not emulation artifacts. The process survived a background/foreground cycle; one launch crashed inside Hermes before posting (the same crash family seen on the iOS simulator). No listening, latency or interruption measurement was made. Raw files: `docs/evidence/2026-09-12/physical-android/`.

**Offline rendering decision (2026-09-12).** Because native offline contexts cannot sum inputs or delay, and browser DSP internals differ per vendor, `Engine.render` renders projects with TuneJS-owned DSP in plain JavaScript (Web Audio-specified biquad and pan laws, ideal oscillators, the same envelope event lists the live voices use, integer-frame delays, FFT convolution of the synthetic reverb response, TuneJS resampling). It claims offline-to-offline determinism — verified byte-identical across repeated renders in Node and headless Chrome — and explicitly does not claim sample equality with live host output. This is the first TuneJS DSP module; it is the natural basis for the worklet-based effect and binaural path that native parity needs.

**Fixture-version-6 correction.** The same fan-out/fan-in probes routed through one summing GainNode also deliver a single input natively (0.5 instead of 1.5; 1 instead of 2; identical on both platforms). The earlier inference that GainNode fan-in sums was unfounded: the timing fixture's twelve sources are never simultaneously active. In the native OfflineAudioContext, simultaneous inputs to any node are not summed. This is decisive for polyphony if it also holds in the live AudioContext (three instrument voices feed one filter), so a live-context probe measured through an AnalyserNode with muted output is the next Wave 2 measurement before any further native capability claim. The master GainNode remains as output structure but does not resolve the defect. Raw files: `docs/evidence/2026-09-12/topology-v6/`.

## Wave 2 capture-boundary source findings

Inspection of the installed React Native Audio API 0.13.3 source establishes limitations of the existing callback path, not measured device loss:

- `common/cpp/audioapi/core/utils/AudioRecorderCallback.cpp`, `invokeCallback()`, sets `when = framesEmitted_ / sampleRate_` and then advances `framesEmitted_` by the emitted buffer length. This is an emitted-PCM counter, not a hardware acquisition timestamp or the engine clock. Sampling `engine.currentTime` when the JS callback arrives cannot remove queueing delay or reconstruct a hardware-clock anchor.
- `ios/audioapi/ios/core/utils/IOSRecorderCallback.mm` and `android/src/main/cpp/audioapi/android/core/utils/AndroidRecorderCallback.cpp`, `receiveAudioData()`, return without forwarding a buffer when their input pool has no free slot. Those branches do not advance the emitted-frame counter or report a dropped-frame count. Consequently, contiguous callback `when` values alone do not establish loss-free acquisition. These branches were inspected, not forced on a device in this wave.
- `common/cpp/audioapi/events/AudioEventHandlerRegistry.cpp` forwards payloads through an asynchronous React Native call invoker. The recorder uses the general `dispatchEvent()` enqueue path. A bounded input pool or TuneJS consumer queue does not establish a bound on all pending native-to-JS payloads; this path needs an end-to-end delivery bound.
- A graph-side alternative exists in `WorkletProcessingNode.cpp`: processing callbacks receive the context's current time. This is a candidate for engine-clock bus observation, not a validated capture solution. `RecorderAdapterNode.cpp` reads a ring buffer and zero-fills missing input; its ring-buffer implementation can discard old input without exporting discontinuity metadata. Routing microphone data through that node does not by itself recover the missing acquisition history.

**Decision:** do not implement the specified native PCM tap by assigning callback-arrival timestamps or assuming contiguous `when` values prove continuity. The capture backend needs a producer-side frame origin mapped to the engine clock, explicit acquisition/drop accounting, and bounded delivery through every queue. Recorder overflow must fail explicitly; a tap must report every discarded range. A targeted native extension or upstream capability is required before claiming that this callback path satisfies those contracts. No microphone permission was requested and no native capture acceptance result is implied by this source review.

## Remaining decision gates

1. Run the built Android app fixtures on a native runtime, and run both platforms on physical phones. Extend the iOS simulator checks to activation, natural voice completion and foreground lifecycle. Record versions, route, permissions, failures, interruptions and native output, not mocks.
2. Evaluate a versioned HRTF integration on browser and native with common pose/movement/reference fixtures. Stable RN 0.13.3 cannot meet the full spatial contract alone. Consider a narrowly scoped spatial extension before replacing every audio primitive.
3. Map native capture timestamps to the engine clock; verify synthetic and microphone streams, slow-consumer gaps and cancellation. Explain the initial browser timestamp discontinuity.
4. Define filter/reverb/HRTF reference buffers and tolerances before acceptance runs. Current repeatability is within one backend; full project determinism and cross-host rendering remain unimplemented.
5. Run the specified reference workload, physical interruption cycles, listening review, memory tracking and wired latency measurement. Underruns and latency are currently reported as unknown, not zero.
